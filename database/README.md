# Database architecture

The active development database is created at
`backend/data/cybershield.db` when the backend starts. This top-level directory
contains architecture notes only.

Phase 7 uses versioned migrations for `complaints`, `users`, `otp_requests`,
`complaint_evidence`, `complaint_notes`, `audit_logs`, status history,
notifications, delivery attempts, preferences, and user-visible messages.
Existing anonymous complaints retain a null owner, while authenticated complaints
receive a foreign key derived exclusively from the server session. OTP values are
stored as keyed SHA-256 hashes with expiry, attempt, and used-state metadata.

Evidence rows use application-generated public IDs, internal complaint foreign
keys, UUID disk names, server-derived MIME types and sizes, SHA-256 integrity
hashes, upload status, and UTC timestamps. File bytes live in the backend's private
evidence directory rather than SQLite or the publicly served frontend. The
foreign key is restrictive so complaint deletion cannot silently orphan files.

Migration 4 adds `users.role` with a checked `user`/`admin` value and a `user`
default, so all existing accounts migrate without recreation. It also adds
append-only internal notes and audit logs with random public references, actor and
complaint foreign keys, JSON-validated narrow metadata, and UTC timestamps.
Indexes cover priority and update sorting, note complaint history, and audit actor,
entity, and time lookups. Status, priority, and note mutations write their audit
events in the same SQLite transaction.

Migration 5 adds `complaint_status_history`, `notifications`,
`notification_deliveries`, `notification_preferences`, and
`complaint_user_messages`. Existing complaints receive one explicit baseline
event labelled as the current status when history tracking was enabled; no earlier
transitions are invented. New submissions and administrator status changes write
history, notification, and internal audit records in the complaint transaction.
External email work begins only after commit. Random public references and unique
event/delivery constraints prevent database IDs and duplicate channel deliveries
from reaching clients.

SQL remains isolated inside repositories, input is parameterized, public IDs are
generated by the application, and timestamps use UTC ISO strings. These boundaries
keep a future PostgreSQL migration focused on the database adapter, SQL dialect,
and a production session-store adapter.

The SQLite database is local, ignored by Git, and contains fictional demo data
only. It is not suitable for collecting real incident reports or credentials.
